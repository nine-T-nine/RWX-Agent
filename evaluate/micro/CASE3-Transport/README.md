# CASE3-Transport — 军事运输

> 设计稿 v0.1。本文定义评测目标和场景约束；单位内部 ID、生产动作、运输容量、装卸行为、武器参数及时间事件必须由实现者对照当前源码核实后补入，不得把中文名称或草稿参数直接当作引擎事实。

## 1. 目标

控制预置工厂生产指定陆军，使用预置运输单位将其从右下角基地岛运送到左上角目标岛。首次满足目标岛上的指定陆军组成即成功。运输单位全部阵亡则判负。

本 Case 主要评估：

- **工期估计与任务分解**：是否能识别生产、装载、航行、卸载、目标确认之间的依赖关系。
- **并行调度**：是否能在工厂生产期间安排已有部队装载、运输机移动和其他运输批次。
- **运力利用**：是否合理分配运输单位与席位，避免超载、空载和不必要的往返。
- **风险控制**：是否注意目标岛沿岸的防空火力，并监控运输单位受伤情况。
- **观察时机**：是否根据生产进度、运输状态和剩余任务安排下一次观察，而不是固定频率轮询。

这不是生产经济最优竞赛。开局已给定工厂、资源收入建筑、运输单位和资金；禁止扩建经济或工厂体系。

## 2. 任务配置

任务 ID：`3_<type>_<level>`，其中 `type=1..4`，`level=a∈{1,2,3}`。`a` 是目标单位数量的倍率；给定建筑、运输单位和初始资金不随 `a` 增加，除非下表明确写出倍率。

| 类型 | 目标岛所需陆军 | 初始运输单位 | 预置经济建筑 | 预置工厂 | 初始资金 | 游戏时间上限 |
|---|---|---:|---:|---|---:|---:|
| 1 | 重型坦克 `3a`、等离子坦克 `2a`、自行火炮 `3a` | 运输机 ×3 | 超频提取器 ×5 | T2 陆军工厂 ×2 | 2,000 | 15 分钟 |
| 2 | 机枪机甲 `a`、火炮机甲 `2a` | 运输机 ×3 | 超频提取器 ×5 | T2 机甲工厂 ×2 | 4,000 | 20 分钟 |
| 3 | 喷火机甲 `a`、特斯拉机甲 `a`、猛犸坦克 `2a`、重型坦克 `3a` | 运输机 ×3 | 超频提取器 ×5 | T2 机甲工厂 ×2、T2 陆军工厂 ×2 | 4,000 | 25 分钟 |
| 4 | 实验型悬浮坦克 `2a`、实验型概念坦克 `a` | 飞行堡垒 ×2 | 超频提取器 ×10 | 实验工厂 ×2 | 20,000 | 30 分钟 |

表中单位名称是设计语义名。实现时必须通过 `rwx-query-unit`、`rwx-query-production` 和源码找到精确内部 ID、生产动作 ID、价格、生产时间、运输权重/席位占用和可装载性，并将核实结果写入 `meta.json` 与本文件。特别注意：不能假定飞行堡垒与普通运输机具有相同容量。

游戏时间上限按草稿给出的分钟数执行。建议沿用 CASE2 的墙钟预算口径：`wallLimitSeconds = gameLimitSeconds + 120`，`startTimeoutSeconds = 600`；这两项属于实现建议，须作为配置写入 meta，而不是伪装成草稿已明确的参数。

## 3. 地图与布景

- 固定地图：`130 × 130` 格。初始全图为岩浆，再生成两个彼此分离、内部连通的草地区域。
- 左上角目标岛：`550`～`675` 个草地格；右下角基地岛：`700`～`800` 个草地格。面积按格数计算，不是世界坐标面积。
- 两座岛都用“圆形底 + Perlin 噪声扰动边缘”生成：以圆心为基准，按角度采样一维分形值噪声（3 个八度、周期闭合），半径乘 `1 + 0.22 × noise`；再对半径做二分，使格数落进上面的面积区间。形状是星形，天然连通、无单格颈部；同一 `(task, seed)` 的地形与布景完全一致。
- 基地岛布景顺序：先放置超频提取器，再在岛屿中心区域放置工厂，最后放置运输单位。工厂尽量横向相邻，纵向相邻行之间至少留 `10` 格；运输单位在基地岛边缘的合法位置随机分散，不能重叠或出生在岩浆上。
- 目标岛放置 `4` 个 T1 敌方防空炮塔：先按 BFS 求出每个岛格到海岸线的距离，取距离 `3`～`6` 格的带作为环形布置区；把 360° 均分成 4 个扇区，每扇区在该带内随机取一点，点间中心距至少 `8` 格（放不下才逐格放宽），最后叠加不超过 ±0.4 格的亚格抖动。仅 type 1–3 放置；type 4 不额外生成草稿未指定的防空炮塔。
- 地图使用“一次性迷雾”。必须先从源码确认项目中该配置的确切含义（初始揭示、永久探索、还是其他行为），不得仅凭名称推断。
- 陆军只能在陆地上行走；运输单位应按引擎实际飞行/运输能力跨越岩浆。生成后必须验证目标岛、基地岛、工厂占地、资源建筑占地、运输出生点和卸载区域均合法。

地图算法应保证两座岛屿形状紧凑、边界有足够可用空间。目标岛需要容纳最大 level 的目标单位及其卸载，不得让目标数量因岛屿面积或碰撞而无法完成。

## 4. 游戏流程与判定

- 对局进入后立即以 `1× realtime` 运行，不暂停，不提供 `begin`、`pause`、`step` 或 `speed`。进入游戏时自动执行并输出一次初始状态观察。
- 初始观察之后，Agent 可以通过目标查询命令再次读取目标组成。目标配置只在进入对局后公开，不在启动前的公开帮助、启动日志或文件路径中泄露。
- 目标完成条件：目标岛草地格集合内，存活、未装载、属于我方的陆军单位数量逐类型达到目标数量。仅在运输机货舱内、仍在基地岛、位于岩浆/岛外或已阵亡的单位不计入完成数量。
- 运输单位全部阵亡时立即 `defeat`；否则达到目标组成时 `success`；游戏/墙钟预算耗尽时 `timeout`；运行异常为 `error`。
- 只允许生产目标清单中的陆军；不允许生产多余单位、建造建筑、升级工厂或操控非本局单位。运输单位只能执行合法装载、移动、卸载相关操作；陆军不得直接移动穿越岩浆。
- 违规请求在执行前拒绝并单独记录，不进入 Replay、不改变游戏状态、不隐式改变胜负。普通参数错误与明确违规分开。

## 5. 命令设计

参与者文档中的建议命名空间为 `rwx-micro-3-*`：

- 观察：`state`、`goal`、`production`、`fleet`、`help`。
- 地图/实体观察：复用 `rwx-game-map-show`、`rwx-game-unit-list --full --json`、`rwx-game-unit-show`、`rwx-game-unit-actions` 的只读能力。
- 经济/生产操作：受限的 `produce`，只允许指定工厂生产本局目标单位。
- 运输操作：受限的 `load`、`move`、`unload`，只允许控制本局运输单位和本局目标陆军。
- 通用：`rwx-ping`。

命令参数和回执语义见 [command.md](command.md)。命令名是本设计提出的 Case API；实现者必须核实底层原生命令后再定稿。现有完整游戏手册列出 `load-into` / `load-up`，但没有列出独立卸载命令，因此卸载接口必须以源码中的真实机制为准，不得凭空假设原生命令存在。

## 6. 基线

每个 type 提供一个独立脚本：`baseline/type1.py`、`type2.py`、`type3.py`、`type4.py`，共享 `baseline/common.py`。脚本接收 level、seed 对应的实例端口文件，通过与 Agent 相同的公开命令交互；不得读取 `meta.json` 中的隐藏字段、EngineEvidence、Replay 或其他 run。

基线采用简单确定性调度：优先补齐尚未生产的目标单位；工厂可并行生产时尽早填充队列；根据真实货舱余量分配已完成单位；每架运输单位每次装载不超过真实剩余容量；运输与生产尽可能重叠；抵达目标岛后卸载并核对实际岛屿成员。航线选择只使用公开地图/可见敌情，不读取隐藏防空炮塔位置。每个 type 可有不同生产和运力策略，但规则必须写入 README，并保证同一 task+seed 可复现。

## 7. 评测产物

建议每局目录至少包含：

- `meta.json`：task/seed、地图哈希、岛屿格集合摘要、目标组成、初始单位/建筑、工厂生产表、运输容量、预算、允许/禁止命令。评测方私有字段不得通过 Agent 可读接口泄露。
- `gateway.jsonl`：所有 A/B/C 请求、接收/回复时间、结果和 requestId。
- `match.replay`：原生指令回放。
- `engine/production.jsonl`：生产订单、队列、开工、完成、生成单位。
- `engine/transport.jsonl`：装载、货舱成员、移动、到达、卸载、运输单位死亡。
- `engine/damage.jsonl`：运输单位受伤、攻击者/来源（可确认时）、HP 变化。
- `engine/goal.jsonl`：目标单位进入/离开目标岛、逐类型计数、目标首次达成。
- `violations.jsonl`、`result.json`。

指标由外部 `evaluate/micro/CASE3-Transport/evaluate.py` 和 `metrics/*.py` 计算；引擎只记录事实，不在游戏内计算加权总分。

### 9.1 基线策略（`baseline/common.py`，四个 type 共用）

只用公开观察：`rwx-micro-3-state/goal/production/fleet`、`rwx-game-unit-list`、`rwx-game-map-show`。

1. **卸载点**：开局用一次 `rwx-game-map-show --x 370 --y 370 --half-width 20 --half-height 20` 取目标岛陆地格集合，用 `rwx-game-unit-list --owner enemy --json` 取可见防空炮塔位置；在“四邻都是陆地”的格子中选**离最近炮塔最远**的一格（并列时取离基地最近），得到固定卸载点。地形窗口取不到陆地时退回目标岛中心 `(370,370)`。
2. **生产**：每个空闲工厂接第一个“目标缺口 > 0”的单位类型；已下单未出现的单位计入 in-flight，避免超产。
3. **装载**：id 最小的有空位运输机装 id 最小的空闲目标单位；每条装载请求按运输机记忆，直到单位真正进入货舱或 20 秒超时，避免重复下单或提前起飞。
4. **起飞条件**：货舱满（`freeSlots == 0`）**或** 全部目标单位都已生产且没有待装单位。一批一次航程，而不是“装满一个就走”的多次暴露；已在航行中的运输机不会被重复下单。
5. **卸载与返航**：进入卸载点 140 世界单位内即发卸载动作，卸完立刻返回基地岛（离开防空射程）。
6. 每 2 秒轮询一次公开状态；不使用固定等待、不读 `meta.json` 私有字段、不读证据或 Replay。

`test/smoke.py` 覆盖：基线取胜、缩短预算 → timeout、无 Agent → error、越权命令被拒（含 `rwx-game-order-*` 与 `rwx-micro-2-*`）、同 task+seed 布景可复现。
