# Stage1 完整对局实时性评分（`stage1-v2`）

本文件是**第一轮完整对局评估的唯一细则来源**：材料要求、统计口径、12 个扣分项的规则、环境健康门，以及
**哪些扣分项在人类对局里算不出来**。管理员启动对局的流程见[评测管理员指南](README.md)。

Stage1 从 100 分开始，只评价 Agent 在 1× 实时对局中的**反应速度与下令节奏**。战术优劣、情报选择、命令是否有效、
格式错误只保留为材料，不扣这张实时性分。

> 版本前提：`score.json` 的 `version=stage1-v2` 才可互相比较。健康门异常或样本不足时分数标 `provisional`，
> 不得与正常环境直接混榜。旧 `stage1-v1` 分数不可与本版混榜。

**读法**：§1–§4 讲"分数从哪来"，§5–§7 讲"每一项怎么算"，§8 讲"人类对局算不算"，§9–§10 讲"什么不计分"，
§11 是样本与审计附录。只想知道扣分项的人直接看 §5。

## 1. 材料要求

### 1.1 两份输入，缺一不可

一局要用**同一局、同一队伍**的两份材料：

| 材料 | 来源 | 提供什么 |
|---|---|---|
| `commands-<对局>.txt` | CLI 端口录制（启动时加 `--evaluate <档位>`） | 高层命令：游戏时间、玩家、命令名、参数。A/B/C 分类和 A→B、B→A 间隔都来自它 |
| `replays/<对局>.replay` | 从 tick 0 开始录制（`rwx-battleroom-start --record`） | 游戏实际提交的底层命令，用于底层节奏和映射 |

- 中途 `rwx-game-replay-start` 的 Replay 缺少开局过程，**不能**作为完整评估材料。
- 命令行录制后先落在 `evaluate/output/`，由 [`tools/match_materials.js`](tools/README.md) 搬进对局目录；
  连续多局共用一个文件时，先按 `match` 拆成单局。
- 一局的材料只放一个目录，命令日志、`replays/<对局>.replay`、对局目录三者同名，`meta.json` 记这一局的身份。

### 1.2 准入门槛（硬性）

以下任一不满足**直接拒绝生成报告**，不产出 `score.json`：

- 端口日志中的有效对局时长 **> 300 秒**（恰好 5:00 不算）；
- A+B 命令数 **> 50**（恰好 50 不算）；
- 必须是单一对局、单一玩家，且游戏时间不回退。

### 1.3 处理流程

`Replay → replay.py → Replay JSONL → evaluate_stage_1.js`。端口命令与 Replay 按队伍、命令类型、
单位/目标/坐标/动作语义及保守时间窗关联；**一个底层记录只分配给一个高层请求**。证据不足时保留
`partial`、`ambiguous`、`unmatched` 或 `unobservable`，不按最近时间强行归属。

**匹配只表示找到提交痕迹，不表示单位已完成移动或生产。**

新对局必须先跑 `evaluate/preprocess.js`，用 `prepared/` 里裁剪过的材料；否则投降后、胜利后的尾部轮询会抬高
A 命令数、拉长结尾静默区间，把节奏分算歪（见[总 README](README.md#对局结束后的评分流程)）。

```powershell
python evaluate/utils/replay.py "replays/<对局>.replay" --commands "evaluate/output/<对局>/commands-<对局>.txt"
node evaluate/preprocess.js "evaluate/output/<对局>"
node evaluate/evaluate_stage_1.js "evaluate/output/<对局>/prepared/commands-<对局>.txt" "evaluate/output/<对局>/prepared/replay.jsonl"
```

## 2. 产物

全部写在 `evaluate/output/<对局>/stage_1/`：

| 文件 | 用途 |
|---|---|
| `report.html` | 图表、映射明细、指标和逐项扣分的主要入口 |
| `stage1_metrics.json` | 可机器读取的完整指标；含评分证据、历史四档分布和只记录项 |

## 3. 统计口径

| 名称 | 定义 |
|---|---|
| A / B / C | A 是查询；B 是操作或配置；C 不参与 A/B 节奏 |
| 行动指令 | 直接 `rwx-game-order-*`；不含 `keep-set`、`auto-set` 等配置 |
| A→B 决策周期 | 连续 A 块首条到紧随其后的 B 块末条 |
| B→A 等待 | 相邻命令中的末条 B 到下一条 A |
| `>30s` 空窗占比 | 相邻行动指令间隔超过 30 秒时，整段时长之和除以对局时长（结尾另算） |
| 底层间隔 | 我方 Replay 中相邻两条有效底层命令的游戏时间差；含自动微操/UI，同 tick 的 0 秒保留 |
| 无落地痕迹 | 直接 B 在保守映射窗口内没有唯一 Replay 记录；**不等于已证明执行失败** |
| 首个建造者生产 | 首次 `order-action` 或 `keep-set` 的 `u_builder/u_builderShip/u_combatEngineer/u_mechEngineer`；首个军事生产仅保留为材料 |

所有时长都是**游戏时间**。旧 `[MM:SS]` 日志的高→低延迟使用 `delayMin`，避免把缺失的毫秒精度扣给 Agent。

## 4. 底层命令的提交者归属

Replay 只记录"某 tick 有命令提交给某些单位"，分不清是 Agent 下的、补产规则补的还是 auto-set 微操发的。
`telemetry.jsonl` 的 `native` 行带 `source`：

| source | 含义 |
|---|---|
| `agent` | Agent 通过 CLI 下发的直接命令 |
| `pending` | `--allow-unaffordable` 等待发命令最终落地的那一次 |
| `keep` | `keep-set` 补产规则自动补的 |
| `auto` | `auto-set` 微操下发（`AiAutomate` 打标；2026-11-02 之后的对局才有） |
| `engine` | 其它没走 CLI 服务的提交：AI、UI，以及打标之前的 auto-set |
| `unknown` | 有 Replay 记录但找不到对应提交行 |

两者是同一条提交流，时间差一个 tick（Replay 记生效 tick，telemetry 记提交方运行的 tick）。按（单位集合，±1 tick）
做一对一指派，实测 5400 余条里只有 3 条对不上——都是命令发生在 telemetry 覆盖结束之后。

**两条结论**（7 份带实时 telemetry 的样本，其中一局 1189 条底层命令只有 73 条来自 Agent）：

1. 底层命令的绝大部分**不是** Agent 下的。把补产和微操算成"Agent 的操作频率"会严重高估。
2. Agent 命令**全部**被高层请求认领：未被任何高层请求占用的底层记录 100% 是 `keep`/`engine`。

因此 `stage1_metrics.json` 增加 `attribution` 与 `native.agentCommandCount` /
`agentProductionCommandCount` / `agentIntervals`，报告单列一行。

> **扣分口径不变**：A4 仍按全部底层命令统计。把补产和微操排除后，Agent 自己的命令会显得更稀疏，
> 直接据此扣分等于惩罚"用自动化"这种正当策略。自动化只出材料。

**实时 telemetry 不是第一轮评分的必需输入。** 没有它时，自动归属只在可证明的 `keep-set` 情况下推断，其余记
`unknown`。4 份旧样本的 telemetry 是在回放时写的，`source` 全是 `replay_unknown`，`attribution.telemetry=false`，
指标退回"全部底层命令"口径，**不可与有 telemetry 的样本直接比较**。

## 5. 扣分项总表

12 项，各自先裁到 `[0,cap]`、保留 1 位小数再求和，`总分 = max(0, 100 − Σ)`。**各项上限之和可超过 100。**

`人类`列 = 人类对局（无 CLI 命令日志，见 §8）能否统计：✅ 可以，⚠️ 技术上可但需绕过入口，❌ 不能。

| ID | 项目 | 规则 | 上限 | 人类 |
|---|---|---|---:|---|
| `A1-first-order` | 首个行动指令 | 线性 `0→5:0→5`、`5→8:5→8`、`8→20:8→12`、`20→60:12→15` | 15 | ❌ |
| `A1-first-mining` | 首个采矿建造 | 线性 `0→20:0→5` | 5 | ❌ |
| `A1-first-builder` | 首个建造者生产 | 线性 `0→30:0→5` | 5 | ❌ |
| `A2-decision-cycle` | A→B 去离群均值 | 线性 `5→15:0→4`、`15→30:4→8` | 8 | ❌ |
| `A2-wait-after-action` | B→A 去离群均值 | 线性 `3→8:0→5`；自然指数 `8→25:5→18` | 18 | ❌ |
| `A2-wait-outliers` | B→A 离群值 | 每个离群值到去离群均值的距离：`(0,20)`/`[20,40)`/`[40,60)`/`[60,∞)` 秒 → `0.8/1.2/1.5/2` | 10 | ❌ |
| `A2-decision-outliers` | A→B 决策离群值 | 只计 `A_count/(A_count+B_count)>50%` 的周期；距离 `(0,30)`/`[30,60)`/`[60,∞)` 秒 → `0.5/0.8/1.5` | 8 | ❌ |
| `A4-native-cadence` | 相邻底层间隔 | 权重档 `≤3s`=0、`(3,5)`=1、`[5,12)`=3、`[12,25]`=8、`(25,∞)`=20；`K=Σ(占比×权重)/20`；扣 `15K` | 15 | ⚠️ |
| `A5-AA` | A→A 离群占比 | `<5%` 不扣；自然指数 `0.05→0.75:2→8` | 8 | ❌ |
| `A5-BB` | B→B 离群占比 | `<5%` 不扣；自然指数 `0.05→0.75:1→8` | 8 | ❌ |
| `A4-production-rate` | 底层生产指令/分钟 | 二次 `0→8:6→0`，`a=−2` | 6 | ⚠️ |
| `A5-query-action-ratio` | A/B | 无 A 直接 10；`0→0.3:10→0` 与 `3→8:0→10` 两段 `a=3`；`[0.3,3]` 不扣；`>8` 扣 10；有 A 无 B 按无穷大 | 10 | ❌ |

术语：`线性 l→h:y0→y1` 等均按 §6 的原坐标公式；低于首个端点取低端值，高于末端取高端值。

## 6. 曲线与横轴

横轴直接使用**原始秒数**；比例使用小数（30%=0.3），不将区间归一化后再应用曲线。给定端点 `(l,y0)`、`(h,y1)`：

- 线性：`y = y0 + (y1−y0)(x−l)/(h−l)`。
- 指数段统一写成平移形式 `y = exp(x−a)+b`，其中 `a=l−ln((y1−y0)/(exp(h−l)−1))`，`b=y0−exp(l−a)`；这样严格通过 `(l,y0)` 与 `(h,y1)`。
- 对数段统一写成平移形式 `y = ln(x−a)+b`，其中 `r=exp(y1−y0)`、`a=(r·l−h)/(r−1)`、`b=y0−ln(l−a)`，要求整段 `x>a`。
- 二次：`y = a·x² + b·x + c`，`b=(y1−y0−a(h²−l²))/(h−l)`，`c=y0−a·l²−b·l`；给定的 `a` 保持原值。

区间外沿用端点；区间内越界的扣分裁到 `[0,cap]`。例如底层生产率在 `[0,8]` 上是 `−2x²+15.25x+6`，
区间内可能大于 6，裁为 6；A/B 高比例段在 `[3,8]` 上是 `3x²−31x+66`，负值裁为 0。

## 7. 逐项规则

### 7.1 开局里程碑（A1）

三项都取"从开局（游戏时间 0）到第一个该类事件"的秒数，**缺失（整局没有该事件）扣满该项上限**。

| 项 | 事件 |
|---|---|
| 首个行动 | 首条直接 `rwx-game-order-*` 的时间 |
| 首个采矿建造 | 首个 `rwx-game-order-build` 且 `type` 为 `extractor` / `extractorT1`（允许 `custom:` 前缀） |
| 首个建造者生产 | 首个 `rwx-game-order-action` 或 `keep-set` 的 `u_builder`/`u_builderShip`/`u_combatEngineer`/`u_mechEngineer` |

首个军事生产（`u_` 开头且不是建造者/侦察单位）、`>30s` 行动空窗、结尾静默**只保留材料**，不扣分。
行动空窗按相邻直接 order 的间隔统计，超过 30 秒的间隔整段计入占比，不设惩罚。

### 7.2 决策与等待（A2）

- 两项均值都先**去离群**再求均值；离群识别见 §7.5。
- **没有周期/等待样本时，该均值项和对应离群项扣 0**（不是扣满）。
- `A2-wait-outliers`：对每个离群值按"它到去离群均值的距离"分档扣分，累计后封顶 10。
- `A2-decision-outliers`：先按 `A_count/(A_count+B_count)>50%` 过滤周期，再对过滤后的离群值分档；
  这个条件**只影响离群扣分**，不改变 `A2-decision-cycle` 的均值。

### 7.3 底层节奏（A4）

- 分母是**全部相邻底层间隔**（含 0 秒、含补产与微操），四档权重 `0/1/3/8/20`；
  草稿里没写清的精确 12 秒、25 秒边界都落在第三档 `[12,25]`（`12` 不满足 `<12`，`25` 满足 `<=25`）。
- `K = Σ(档位样本占比 × 权重) / 20`，扣 `15K`；`K` 最大 1，即该项最多 15 分。
- `A4-production-rate` 只数我方 Replay 里的生产类底层命令，除以对局分钟数。

### 7.4 离群占比（A5-AA / A5-BB）

- `AA` = A→A 相邻间隔的离群值占比；`BB` = B→B 相邻间隔的离群值占比。
- `<5%` 不扣；`≥5%` 按自然指数到 75% 处封顶（上限 8）。
- 样本不足 4 个时不标离群，占比按 0 计。

### 7.5 离群识别

沿用稳健阈值：至少 4 个样本时，`max(Q3+1.5IQR, median+3×1.4826MAD, median+5s)`，
**严格大于**阈值才算离群。A→B、B→A 分别对全部同类样本识别并计算去离群均值。
原有四档 `normal/mild/moderate/severe` 仍输出以便对照历史，**已不驱动扣分**。

### 7.6 A/B 比例（A5-query-action-ratio）

- 没有任何 A：直接扣 10。
- `A/B ∈ [0.3, 3]`：不扣。
- `A/B < 0.3`：`0→0.3` 上从 10 降到 0（`a=3`）。`A/B > 8`：直接扣 10；
  `(3,8]` 段 `3→8` 上从 0 升到 10（`a=3`，与上一段共用同一二次式）。
- 有 A 无 B：按无穷大处理，扣 10。

## 8. 人类对局：哪些扣分项算不出来

**定义**：人类对局 = 玩家直接用鼠标/键盘在 GUI 打完一局，**没有发出任何 CLI 请求**。因此没有
`commands-*.txt`，也没有 `gateway`/`result` 回执。带 `--evaluate` 启动仍会打开 CLI 与命令录制，但鼠标操作
不会写进命令日志。

### 8.1 结论

| 情况 | 结果 |
|---|---|
| 按本文入口跑人类对局 | **整份报告不生成**：A+B 命令数为 0，过不了 §1.2 的 `>50` 门槛；连队伍归属都取自命令日志 |
| 只取"技术上只依赖 Replay"的两项 | `A4-native-cadence`、`A4-production-rate` 可以单独实现（需显式给队伍号），但要另写入口，不属于现行流程 |
| 其余 10 项 | **全部不可统计**——它们全部由 A/B 命令序列或 A 类查询时刻定义 |

逐项原因：

| 项 | 缺少的输入 | 能否用别的东西代替 |
|---|---|---|
| `A1-first-order` / `A1-first-mining` / `A1-first-builder` | 首条 A/B 的游戏时间 | 不能。Replay 只有底层命令，没有"这是一个查询"的语义 |
| `A2-decision-cycle` / `A2-wait-after-action` | A 块与 B 块的边界 | 不能。没有 A/B 分类就没有"决策周期" |
| `A2-wait-outliers` / `A2-decision-outliers` | 同上 | 不能 |
| `A5-AA` / `A5-BB` | A 序列、B 序列 | 不能。底层序列不是 A/B 序列 |
| `A5-query-action-ratio` | A 与 B 的条数 | 不能 |
| `A4-native-cadence` / `A4-production-rate` | 只要 Replay + 我方队伍号 | **可以**，但现行入口仍要求命令日志 |

### 8.2 因此不要做的事

- 不要用"底层命令间隔"冒充人类的 `A2` 节奏，也不要把人类的鼠标操作折算成 A/B 计数。
- 不要把人类对局的 100 分直接与 Agent 的 `stage1-v2` 并列：人类局根本没有生成分数，
  缺分不等于满分。
- 人类局没有现成的自动分数可拿：Stage2 同样拒算（见 [STAGE2_SCORING.md §6](STAGE2_SCORING.md#6-人类对局哪些扣分项算不出来)）。
  可用的对照价值在回放本身——战术行为、决策顺序、单位损失过程——以及人工复核，不在这些自动分里。

## 9. 环境健康门（不是 Agent 扣分项）

高层→底层即时延迟只选**唯一匹配且不带** `--allow-unaffordable` / `--after-upgrade` 的直接命令：

- 去异常均值必须 `< 0.5s`；
- 离群占比必须 `< 5%`；
- 两项同时满足为 `normal`，不满足为 `abnormal`，没有即时完整匹配时为 `unknown`。

后两种情况都把总分状态改成 `provisional`。待发命令等待资金/升级的时间属于**命令语义**，
不能当成系统投递延迟。

## 10. 只记材料、不计分

以下数据写入 `stage1_metrics.json` 和 HTML，但不加入实时性分：

| 类别 | 输出 |
|---|---|
| B1/B2/B3/B5 感知与查询策略 | 敌方 unit-list、events、threat-list、规则查询、固定空间锚点集中度 |
| C1 无落地 | 原始比例，以及扣除命令风暴整组后的比例 |
| C2 命令风暴 | 同签名至少 5 条、中位间隔 ≤10s、无落地率 ≥80% 的组 |
| C3 格式错误 | 缺单位、目标、坐标、动作或建筑类型的直接 order |
| A6 批量静默 | B 块至少 5 条，块后超过 30s 才出现下一条 A/B |

`partial` 表示只有部分显式单位/数量落地；`ambiguous` 表示多个高层请求竞争同一批底层证据。
**两者都不能改写成"失败"。**

### B. 映射审计结论（2026-11-02）

审查仓库现存 11 份 Stage1 报告，共 1215 条直接 B（其中 236 条未匹配）；7 份带 `command`/`result` 回执
可交叉核验，4 份是旧 telemetry（没有 command/result 行）。

**正向**：没有发现已匹配行的错误归属。

**反向**（对每条未匹配的直接 B，忽略时间窗，在全部底层记录里搜同签名记录）：

| 情况 | 条数 | 判定 |
|---|---:|---|
| 窗口内存在**未被占用**的同签名记录 | **0** | 没有漏配——凡是能配的都已经配上 |
| 窗口内记录已被同签名重试请求占用 | 4 | 4 条回执均为 `INSUFFICIENT_CREDITS`（被拒），保持未匹配正确 |

只取有回执的 7 份看：48 条未匹配里 **42 条被引擎明确拒绝**、3 条 `ACCEPTED`、3 条超出 telemetry 覆盖。
`ACCEPTED` 的三条都是待发命令（`action --units 7 --action extractorT3_0 --allow-unaffordable` 于 244.4 s/544.3 s；
`action --units 11 --action 110 --after-upgrade --count 3 --allow-unaffordable` 于 249.9 s），
它们等资金/升级，等到对局结束也没凑齐，不能编造执行时刻。
**在有证据的样本里，没有一条未匹配是"执行了但没配上"。**

**反方向的剩余量**：没有被任何高层请求占用的底层记录每局 23–1116 条，其中约 94% 是 `move`/`attackMove`，
与 `keep-set`（自动补产）和 `auto-set`（自动微操）对应——它们是 CLI 自动化直接提交的原生命令，
本来就没有一对一的 Agent 请求，不是"漏配的 Agent 命令"。

Claude2 的 136 条 `extractorT3_0` 构成两组命令风暴；原始无落地为 `150/483`，整组排除后为 `16/347`。
原始值和调整值都保留。映射规则仍坚持"宁可 unmatched/ambiguous，不按最近时间强配"；
具体键、时间窗与逐条限制见每份 `mapping_rules.json` 和 HTML 的映射表。
