# Stage1 完整对局实时性评分

Stage1 v2 从 100 分开始，只评价 Agent 在 1× 实时对局中的反应与下令节奏；战术优劣、情报选择、命令是否有效和格式错误只保留材料，不扣这张实时性分。

> 这是初版规则。`score.json` 的 `version=stage1-v2` 是比较前提；映射延迟健康检查异常或没有足够样本时，分数标记为 `provisional`，不得与正常环境直接混榜。

## 材料收集与处理逻辑

第一轮需要两份同一局、同一队伍的输入：

1. `commands-<对局>.txt`：CLI 端口记录的高层命令，包含游戏时间、玩家、命令与参数。开启评估采集（`--evaluate <档位>`）并使用 CLI 后生成；连续多局共用一个文件时，先按 `match` 拆成单局。
2. 从 tick 0 开始录制的 `*.replay`：提供游戏实际提交的底层命令。只录中途 Replay 会缺少开局过程，不能作为完整评估材料。

处理流程是 `Replay → replay.py → Replay JSONL → evaluate_stage_1.js`。端口命令和 Replay JSONL 按队伍、命令类型、单位/目标/坐标/动作等语义及保守时间窗做关联；一个底层记录只分配给一个高层请求。证据不足时保留 `partial`、`ambiguous`、`unmatched` 或 `unobservable`，不按最近时间强行归属。匹配表示找到提交痕迹，不表示单位已完成移动或生产。

实时 `telemetry.jsonl` **不是第一轮评分的必需输入**；若有，它可为 Replay 底层命令补充提交者归属（`agent`/`pending`/`keep`/`auto`/`engine`），用于报告归属分析。按单位集合与相差不超过一个 tick 的时间关联 Replay 和 telemetry。无可用实时 telemetry 时，自动归属只在可证明的 `keep-set` 情况下推断，其余记为 `unknown`；旧回放 telemetry 的 `replay_unknown` 不作为提交者证据。无论是否能区分来源，A4 扣分仍按全部底层命令间隔计算。

分析要求端口日志中的有效对局时长 **大于 300 秒**，且 A+B 命令数 **大于 50**；必须是单一对局、单一玩家且游戏时间不回退。低于门槛时拒绝生成报告。

## 生成报告

先把 Replay 解析成 JSONL，再运行第一轮：

```powershell
python evaluate/utils/replay.py "replays/<对局>.replay" --commands "evaluate/output/commands-<对局>.txt"
node evaluate/evaluate_stage_1.js "evaluate/output/commands-<对局>.txt" "evaluate/output/<对局>/replay/<对局>.jsonl"
```

主要产物都在 `evaluate/output/<对局>/stage_1/`：

| 文件 | 用途 |
|---|---|
| `report.html` | 图表、映射明细、指标和逐项扣分的主要入口 |
| `stage1_metrics.json` | 可机器读取的完整指标；含新评分证据、历史四档分布和只记录项 |
| `score.json` / `score.txt` | 100 分制结果、每项证据、环境健康状态 |
| `summary.json` | 保留原有摘要，并增量加入 `stage1Metrics` / `stage1Score` |
| `execution_matches.jsonl` | 每条直接 `order-*` 的高层→Replay 映射证据 |

## 理解统计口径

| 名称 | 定义 |
|---|---|
| A / B | A 是查询；B 是操作或配置；C 不参与 A/B 节奏。 |
| 行动指令 | 直接 `rwx-game-order-*`；不含 `keep-set`、`auto-set` 等配置。 |
| A→B 决策周期 | 连续 A 块首条到紧随其后的 B 块末条。 |
| B→A 等待 | 相邻命令中的末条 B 到下一条 A。 |
| `>30s` 空窗占比 | 相邻行动指令间隔超过 30 秒时，整段时长之和除以对局时长。结尾另算。 |
| 底层间隔 | 我方 Replay 中相邻两条有效底层命令的游戏时间差；含自动微操/UI，同 tick 的 0 秒保留。 |
| 无落地痕迹 | 直接 B 在保守映射窗口内没有唯一 Replay 记录；不等于已证明执行失败。 |
| 首个建造者生产 | 首次 `order-action` 或 `keep-set` 的 `u_builder/u_builderShip/u_combatEngineer/u_mechEngineer`；首个军事生产仍保留为材料。 |

所有时长都是游戏时间。旧 `[MM:SS]` 日志的高→低延迟使用 `delayMin`，避免把缺失的毫秒精度扣给 Agent。

## 底层命令的提交者

Replay 只记录"某 tick 有命令提交给某些单位"，分不清是 Agent 下的、补产规则补的还是 auto-set 微操发的。`telemetry.jsonl` 的 `native` 行带 `source`：

| source | 含义 |
|---|---|
| `agent` | Agent 通过 CLI 下发的直接命令 |
| `pending` | `--allow-unaffordable` 等待发命令最终落地的那一次 |
| `keep` | `keep-set` 补产规则自动补的 |
| `auto` | `auto-set` 微操下发（`AiAutomate` 打标；2026-11-02 之后的对局才有） |
| `engine` | 其它没走 CLI 服务的提交：AI、UI，以及打标之前的 auto-set |
| `unknown` | 有 Replay 记录但找不到对应提交行 |

两者是同一条提交流，时间差一个 tick（Replay 记生效 tick，telemetry 记提交方运行的 tick）。按（单位集合，±1 tick）做一对一指派，实测 5400 余条里只有 3 条对不上——都是命令发生在 telemetry 覆盖结束之后。

7 份带实时 telemetry 的样本：

| 样本 | Agent 命令 | 全部底层命令 | keep | engine |
|---|---:|---:|---:|---:|
| dsh（Ice） | 33 | 73 | 40 | 0 |
| gpt5.6sol（Ice，未完） | 90 | 1074 | 22 | 962 |
| claudeOpus5.5+dsh | 81 | 354 | 79 | 192 |
| deepseek4.1（11-01） | 74 | 170 | 95 | 1 |
| deepseek掺水 | 130 | 153 | 0 | 23 |
| Kimi 延迟 1 | 53 | 598 | 57 | 488 |
| Kimi 延迟 2 | 73 | 1189 | 78 | 1038 |

两条结论：

1. **底层命令的绝大部分不是 Agent 下的**。Kimi 第二局 1189 条里只有 73 条来自 Agent，其余是 auto-set 微操（1038）和补产（78）。把这些算成"Agent 的操作频率"会严重高估。
2. **Agent 命令全部被高层请求认领**：反向核对里，没有被任何高层请求占用的底层记录 100% 是 `keep`/`engine`，`agent`/`pending` 为 0 条。

上表是 `auto` 打标之前采集的，所以 auto-set 微操都落在 `engine` 列；2026-11-02 之后的对局会拆成 `auto`（微操）和 `engine`（AI/UI 等），统计口径不变。

因此 `stage1_metrics.json` 增加 `attribution` 与 `native.agentCommandCount` / `agentProductionCommandCount` / `agentIntervals`，报告里单列一行。**扣分口径不变**：A4 仍按全部底层命令统计——把补产和微操排除后，Agent 自己的命令会显得更稀疏，直接据此扣分等于惩罚"用自动化"这种正当策略。自动化只出材料。

4 份旧样本（3 份 4P + deepseek4.1 10-29）的 telemetry 是在回放时写的，`source` 全是 `replay_unknown`，无法拆分：这些样本的 `attribution.telemetry=false`，指标退回"全部底层命令"口径，报告中标注不可与有 telemetry 的样本直接比较。

## 计算实时性分数

当前版本为 **`stage1-v2`**，根据 [评分草稿](score_design.md) 实现。旧 `stage1-v1` 分数不可与本版混榜。两阶段各自从 100 分开始，分别展示；总分 `max(0,100−Σ扣分)`。单项先限制到 `[0,cap]`，保留 1 位小数，再求和。各项上限之和可超过 100。

### 曲线与横轴

横轴直接使用原始秒数；比例使用小数（30%=0.3），不将区间归一化后再应用曲线。给定端点 `(l,y0)、(h,y1)`：

- 线性：`y=y0+(y1−y0)(x−l)/(h−l)`。
- 自然指数：`y=y0+(y1−y0)(exp(x)−exp(l))/(exp(h)−exp(l))`，即 `p·exp(x)+q`。实现平移指数以避免溢出，不改变曲线。
- 自然对数：`y=y0+(y1−y0)ln(x/l)/ln(h/l)`，即 `p·ln(x)+q`，要求 `l>0`。
- 二次：`y=a·x²+b·x+c`，`b=(y1−y0−a(h²−l²))/(h−l)`，`c=y0−a·l²−b·l`。给定的 `a` 保持原值。区间外沿用端点，区间内越界的扣分也裁到 `[0,cap]`。

例如底层生产率在 `[0,8]` 上是 `−2x²+15.25x+6`；区间内可能大于 6，裁为 6。A/B 高比例段在 `[3,8]` 上是 `3x²−31x+66`；负值裁为 0。这是指定 `a` 和原始端点的直接结果。

### 扣分项目

表中 `线性 l→h:y0→y1` 等均按上面的原坐标公式；低于首个端点取低端值，高于末端取高端值。

| ID | 项目 | 规则 | 上限 |
|---|---|---|---:|
| A1-first-order | 首个行动 | 线性 `0→5:0→5`、`5→8:5→8`、`8→20:8→12`、`20→60:12→15` | 15 |
| A1-first-mining | 首个采矿建造 | 线性 `0→20:0→5` | 5 |
| A1-first-builder | 首个建造者生产 | 线性 `0→30:0→5` | 5 |
| A2-decision-cycle | A→B 去离群均值 | 线性 `5→15:0→4`、`15→30:4→8` | 8 |
| A2-wait-after-action | B→A 去离群均值 | 线性 `3→8:0→5`；自然指数 `8→25:5→18` | 18 |
| A2-wait-outliers | B→A 离群值 | 每个离群值减去该组去离群均值；距离 `(0,20)`、`[20,40)`、`[40,60)`、`[60,∞)` 秒，分别扣 `0.8/1.2/1.5/2` | 10 |
| A2-decision-outliers | A→B 决策离群值 | 只计周期中 `A_count/(A_count+B_count)>50%` 的离群值；距去离群均值 `(0,30)`、`[30,60)`、`[60,∞)` 秒分别扣 `0.5/0.8/1.5` | 8 |
| A4-native-cadence | 相邻底层间隔 | 全部相邻间隔为分母，`≤3s` 权重 0，`(3,5)`、`[5,12)`、`[12,25]`、`(25,∞)` 权重 `1/3/8/20`；`K=Σ(档位样本占比×权重)/20`；扣 `15K` | 15 |
| A5-AA | A→A 离群占比 | `<5%` 不扣；自然指数 `0.05→0.75:2→8` | 8 |
| A5-BB | B→B 离群占比 | `<5%` 不扣；自然指数 `0.05→0.75:1→8` | 8 |
| A4-production-rate | 底层生产指令/分钟 | 二次 `0→8:6→0`，`a=−2` | 6 |
| A5-query-action-ratio | A/B | 无 A 直接 10；`0→0.3:10→0`、`3→8:0→10`，两段 `a=3`；`[0.3,3]` 不扣；`>8` 扣 10；有 A 无 B 按无穷大处理 | 10 |

草稿中底层间隔遗漏的精确 12/25 秒边界分别纳入第三档；0 秒间隔保留在分母。开局里程碑缺失扣满；没有周期/等待样本时该均值项和对应离群项扣 0。首个军事生产、`>30s` 行动空窗和结尾静默仅保留材料。

离群识别沿用稳健阈值：至少 4 个样本时，`max(Q3+1.5IQR, median+3×1.4826MAD, median+5s)`，严格大于阈值才算离群。A→B、B→A 分别对全部同类样本识别并计算去离群均值；A 占比条件只过滤决策离群扣分，不改变该均值。样本不足 4 个时不标离群。原有四档 `normal/mild/moderate/severe` 仍输出以便对照历史，已不驱动扣分。

## 核对系统是否正常

高层→底层即时延迟只选唯一匹配且不带 `--allow-unaffordable` / `--after-upgrade` 的直接命令：

- 去异常均值必须 `<0.5s`；
- 离群占比必须 `<5%`；
- 两项同时满足为 `normal`，不满足为 `abnormal`；没有即时完整匹配时为 `unknown`。后两种情况都把总分状态改成 `provisional`。

这是环境健康门，不是 Agent 扣分项。待发命令等待资金/升级的时间属于命令语义，不能当成系统投递延迟。

## 复核不计分材料

以下数据写入 `stage1_metrics.json` 和 HTML，但不加入实时性分：

| 类别 | 输出 |
|---|---|
| B1/B2/B3/B5 感知与查询策略 | 敌方 unit-list、events、threat-list、规则查询、固定空间锚点集中度 |
| C1 无落地 | 原始比例，以及扣除命令风暴整组后的比例 |
| C2 命令风暴 | 同签名至少 5 条、中位间隔≤10s、无落地率≥80% 的组 |
| C3 格式错误 | 缺单位、目标、坐标、动作或建筑类型的直接 order |
| A6 批量静默 | B 块至少 5 条，块后超过 30s 才出现下一条 A/B |

`partial` 表示只有部分显式单位/数量落地；`ambiguous` 表示多个高层请求竞争同一批底层证据。两者都不能改写成“失败”。

## 映射审计结论

2026-11-02 审查了仓库现存 11 份完整对局 Stage1 报告，共 1215 条直接 B（其中 236 条未匹配）；7 份带 `command`/`result` 回执可交叉核验，4 份是旧 telemetry（没有 command/result 行）。

**正向**：没有发现已匹配行的错误归属。

**反向**（对每条未匹配的直接 B，忽略时间窗，在全部底层记录里搜同签名记录）：

| 情况 | 条数 | 判定 |
|---|---:|---|
| 窗口内存在**未被占用**的同签名记录 | **0** | 没有漏配——凡是能配的都已经配上 |
| 窗口内记录已被同签名重试请求占用 | 4 | 4 条回执均为 `INSUFFICIENT_CREDITS`（被拒），保持未匹配正确 |
| 只在窗口外有同签名记录 | 141 | 136 条是 Claude2 的 `extractorT3_0` 风暴；3 条回执为资金不足（窗外那条属于后续成功重试）；2 条在 gpt 旧样本 |
| 完全没有同签名记录 | 91 | 35 条有明确拒绝码（`STALE_OBJECT` 15、`INTERNAL` 7、`INVALID_ACTION` 6、`PLACEMENT_BLOCKED` 1、`INSUFFICIENT_CREDITS` 1、无 code 5）；3 条 `ACCEPTED`；3 条发生在 telemetry 覆盖结束之后；50 条属没有回执的旧样本 |

只取有回执的 7 份看，48 条未匹配里 **42 条被引擎明确拒绝**、3 条 `ACCEPTED`、3 条超出 telemetry 覆盖。
`ACCEPTED` 的三条都是待发命令，`accepted` 只表示 CLI 收进了待发队列，不等于引擎执行：

- `action --units 7 --action extractorT3_0 --allow-unaffordable`（244.4 s、544.3 s）
- `action --units 11 --action 110 --after-upgrade --count 3 --allow-unaffordable`（249.9 s）

它们等资金/升级，等到对局结束也没凑齐，不能编造执行时刻。**在有证据的样本里，没有一条未匹配是"执行了但没配上"。**

**反方向的剩余量**：没有被任何高层请求占用的底层记录每局 23–1116 条，其中约 94% 是 `move`/`attackMove`，与 `keep-set`（自动补产）和 `auto-set`（自动微操）对应——它们是 CLI 自动化直接提交的原生命令，本来就没有一对一的 Agent 请求，不是"漏配的 Agent 命令"。

Claude2 的 136 条 `extractorT3_0` 构成两组命令风暴；原始无落地为 `150/483`，整组排除后为 `16/347`。原始值和调整值都保留。

映射规则仍坚持"宁可 unmatched/ambiguous，不按最近时间强配"。具体键、时间窗与逐条限制见每份 `mapping_rules.json` 和 HTML 的映射表。
