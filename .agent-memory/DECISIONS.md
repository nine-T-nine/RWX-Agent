# DECISIONS

按日期追加，一条一句结论 + 简短理由。

## 2026-10-28

- 双源评测按 CLI/Command 原生语义映射全部 19 种 order：建造数量读单条 `buildQueueSize`，rally/stop/cancel/stance 与坐标动作保留独立字段；8 种 group/keep/pending/auto 管理命令记录为间接效果，不强造一对一映射。规则独立到 `evaluate/execution-mapping.js`，双文件入口不变。
- 重复待发请求竞争不足的 Replay 记录时标记 `ambiguous`，不按「最近同签名请求」强行归属，不重复分配、不计延迟；收包日志没有响应或请求 ID，不能把候选存在升级成某次请求已执行。
- 命令收包时间由 `[MM:SS]` 改为 `[MM:SS:mmm]`，大厅为 `[--:--:---]`；完整保留已冻结的 `gameTimeMillis`，统计首部同步。两份评测脚本兼容新旧格式；旧样本不补造毫秒，延迟保留 1 秒区间，新样本按记录的游戏毫秒直接计算。

- 命令记录文件名尾部用 `HH-mm`（记录器启动的本地时间）替代随机编号：文件名要能直接读出是哪一局，随机数没有辨识价值；时分不唯一，所以同分钟再启动或同分钟同地图改名时自动加 `-2`、`-3`，而不是覆盖。时分在改名时保持不变，`-stats` 与日志继续共用同一个 token。
- `new` 聚合窗口 3s→5s，`losses` 保持 3s：反复“重新发现同一单位”按用户要求仍只更新既有聚合，但 5 秒窗口能显著减少修订次数。窗口常量放 `RwxEventProcessor`（`DISCOVERY_WINDOW_MILLIS` / `LOSS_WINDOW_MILLIS`），流式修订与 CLI 分组共用，避免两处漂移。
- 订阅落盘拆成两个各 500 条的日志（observe = `new`/`info`，combat = 其余）：单窗口里最热门的发现事件会挤掉战损记录，拆分后各自滚动，互不挤占；代价是消费方要读两个文件。
- 订阅范围固定为「`new`/`info` 不收窄阵营，`damaged`/`destroyed`/`losses` 按 `allies` 切换」：观察类事件属于共享视野，按阵营丢弃只会让订阅方误以为没发现；生产者目前只产 self 侧 new/info，因此这是把默认语义写死而非改变现有输出。
- 接收器 `compact()` 在 `os.replace` 失败后必须重新打开句柄并退避重试：Windows 上目标被其他进程打开时替换会失败，旧实现把句柄留在关闭状态，写入异常被重连循环吞掉，进程活着但整局不再落盘（本轮 23:49 后 6 分钟空白的成因）。

## 2026-10-27

- 事件 JSONL 接收器在接收侧做二次过滤，只落盘 `kind == "update"`（服务端订阅过滤之外的第二道）：订阅只按 `info`/`allies` 裁剪，仍会送来 `cursor` 占位、`event`/`remove` 聚合维护和 `gap`/`overflow` 诊断，实测一次 500 条抓包里 237 条是 `cursor`；诊断改走 stderr，续传游标仍跟随每一条序列号（含未落盘的），否则重连会误报 `gap` 并重放。
- CLI Agent 持久模式以现有命令行作为 stdin、每条回复输出一行 JSON，复用 framed TCP：保留人工交互与批量兼容，同时明确区分多行及空回复，不改游戏协议；连接失败不自动重发。
- CLI 帮助文档**只改 `agent-operation/help_zh.md`（中文，唯一权威）**，改完后在**最终阶段**把 `agent-operation/help.md` 整体同步成英文版（该文件现为全英文镜像，也是 `rwx-help` 运行时读取的文件，由 `core/build.gradle.kts` 打进 core jar）；不要两边各改一半、也不要先改英文版，中英结构必须一致（标题编号、命令名、参数、代码块、表格行数）。
- 事件 JSONL 接收器只保留最新 500 条记录（滚动窗口）：节点常驻时临时日志不能无限增长，续传仍依赖尾部记录的会话与序列；更早事件只能重新启动游戏从 180 秒/1000 条服务端缓存回放。
- 命令记录文件按首局地图命名（`commands-<地图>-<日期>--<唯一编号>.txt`）：CLI 先于对局存在，启动时用 `commands-lobby-…` 占位，首个有效对局改名并保留同一个随机编号；同进程后续对局沿用首局地图名，地图逐局记在统计首部，避免对局中途再改文件名。
- 事件流使用独立回环端口与 UTF-8 NDJSON 订阅协议（`hello`/`event`/`update`/`remove`/`cursor`/`gap`/`overflow`/`reset`），不复用 CLI 的请求-应答端口；每个订阅连接独立游标与线程，消费者按 `eventId`+`revision` 应用增量，`update` 不得计为新事件。理由是持续推送不适合命令帧协议，且多消费者需要各自回放。
- 聚合身份跨帧优先用贡献事件对象身份；对象被缓存淘汰或同一 3 秒聚合窗口内重新发现时，才在“新记录时间 ≤ 旧记录最后贡献时间 + 3 秒”内回退到目标 ID，避免把很久之后的新遭遇误续成旧修订。
- `--owner any` 表示所有可观测实体（含中立树），但敌人仍只包含当前视野内可见者；unit-list 与 threat-list 共用该实时可见性入口，历史位置不参与实体查询。
- `game-state` 在引擎线程一次读取我方、友军及可见敌军快照，不触发观察采样；事件继续由同一个采集器和处理器查询，文本及 JSON 使用相同报告模型，以保持事件历史和统计语义一致。

## 2026-10-26

- 按用户调查结论下架有问题的核弹录像，删除原片、网页副本及封面，并从媒体生成定义移除以避免再次生成；网站改为三场录像，其他录像保留。
- 命令审计接在 `RwxCliTool.serveClient` 的实际收包入口并在执行前冻结游戏时间与控制玩家，避免只拦截某个发送脚本而漏记；工具主体放 `evaluate/utils` 并随 core 打包，仅改 CLI 自定义逻辑及源目录配置。
- 命令日志使用当前对局分秒，大厅标为 `[--:--]`；通过现有每帧任务队列观察首个有效对局帧，在统计首部保存每局真实进入时间及进入时游戏时间，支持中途加入和连续多局，保持原版引擎与网络协议不变。
- 按用户明确指令同名重建独立公开仓库与 GitHub Pages，先导出并校验干净 main 的自包含备份，再删除远程对象；保留本地历史、上游关系和未提交工作区状态。

- 按关联邮箱仅调整指定的 4 个自有提交为公开维护身份，保留匿名作者字段和第三方上游原始提交；使用账号 ID 对应的 GitHub noreply 邮箱供后续公开提交使用。
- 身份改写保留每个提交的文件树、消息与日期，上游共同祖先仍为 `4b7c4cc`；新的功能基线使用 `20cf9b9 → a7bdfc3`，提交号对照仅保存在仓库外备份。

- 网站使用无依赖 HTML/CSS/JS，源码位于 `web/`，由 GitHub Actions 部署 GitHub Pages；静态网站不直接连接游戏或模型服务。
- 保留四个原始录像并忽略入库，生成完整时长的 1080p/60fps H.264/AAC faststart 副本供网页播放，避免 GitHub 单文件大小限制；提交清单和哈希以便校验。
- `nine-T-nine/RWX-Agent` 是个人开发发布仓库；`origin`/`myfork` 保持原有上游用途，发布单独使用 `publish`，不向原远程推送个人扩展。

- 项目文档中的环境地址改为通用占位符；翻译致谢保留原有署名（按用户后续要求回退该部分改动）。

## 2026-10-24

- 复用原版多人协议，不自建同步：原版是房主调度的确定性锁步，各客户端跑完整模拟；云端只做“常驻房主”。
  重构网络同步（服务器权威、客户端仅显示）超出范围，已向用户说明。
- 不保留 `rwx-local-*` 旧命令别名：文档与实际接口必须一致，测试改为拒绝旧名。
- Headless 用同一引擎、替换窗口/绘制/音频适配，不用隐藏窗口冒充：需要真无 DISPLAY/Wayland 也能跑。
- CLI 端口写入 `agent-operation/tmp/port`（主文件 + 每实例记录、原子写、退出清理）：多实例不能互相覆盖，
  Agent 不应该硬编码端口。
- 投降改走引擎系统命令（`-surrender` 进入回放命令队列），不发送聊天文本：聊天文本不改变对局结果。
- 手动命令优先级高于所有微操规则，重新执行 `auto-set` 才恢复授权：用户反馈 guard 会把 attack-move 单位反复拉回。

## 2026-10-25

- 托管房间复用原版代理房主（`isProxyController`）+ 聊天命令通道，新增 `RwxManagedRoom` 策略模块，不改网络协议：
  原版已有代理房主权限位、`-start/-map/-addai/...` 命令、局中加入和返回大厅的数据包。
- 房主选举只在大厅进行，对局中冻结：用户明确要求“对局中始终不会移交权限”。
- 服务器托管时自己占旁观席，且允许局中加入（`allowJoinInProgress`）：新身份加入自动观战，原玩家重连保留原席位。
- “只剩 AI 或无人”判定为“没有在线非旁观玩家”：服务器旁观席和观战客户端不计入对局玩家。
- 第二局就绪问题的最终修法：客户端每局在 `gameHasBeenStarted` 后补发一次 packet 112（loading=true），回大厅时重新武装。
  依据：服务器 `a(false,0)` 只在所有连接 `connection.D==true` 时才继续，而 D 来自 112 的第二个布尔；
  原版每连接只发一次，且 `returnToBattleroom` 会清 D，于是第二局只能等 15 秒兜底（“Still waiting on: X”）。
  先前“按 isLoading 变化重发”的版本不可靠：地图加载可能在同一 tick 内完成，观察不到 true。
- CLI 选出生点要同时受地图容量限制（`MapMetadata.getNumberOfPlayersInMap` 解析 `[p3]`）：房间 `maxPlayers` 默认可到 10，
  把玩家放到地图没有的出生点会让该阵营开局 0 单位、立刻被判定全灭（实测“had no starting units (Team: B)”）。
- 中途加入观战用“开局时的玩家名字快照”判断，而不是注册回调：客户端在接管已开局的对局时会以新连接重注册，
  只按“新连接/previousName==null”判断会把开局玩家自己踢回旁观。
- “还有没有活人”按“在线连接的玩家名 + 队伍名”匹配 `PlayerTeam`，不看 `connection.player`：切出生点后连接上的
  team 指针会停留在旧的旁观队伍（实测 color=-3、wipe=true），而真实队伍仍有单位。
- 开局后 4 秒准备期内不做“无人则回大厅”判定：队伍和单位在 START 之后才建立，过早判定会把每局都立刻结束。
- 大厅地图预览按**地图名**解析，不用 `room.mapPath`：客户端的 `selectedMapPath` 只在开局包（packet 120）里刷新，
  大厅阶段 `engine.currentMapPath` 还是上一张/背景图，按路径查会一直拿到旧预览。
- 空房重置在托管策略里做：最后一个非旁观玩家离开大厅时恢复 `GameRoomSettings` 默认值并移除残留 AI 槽位；
  AI 槽位在引擎里 `isTeamSpectator==true`（`isAi = isTeamSpectator || isTeamControlledByAI`），只能按队伍颜色区分。
- 服务器直接托管自定义地图：把 `mods/maps` 同步到 `/var/lib/rwx/mods/maps`（818 MB，磁盘够）；
  服务器只按需求扫描清单，不会把地图读进内存，代价只有当前对局那一张。
- 项目记忆放 `.agent-memory/`，`agent-tmp/` 与 `agent-operation/tmp/` 只放临时产物：用户要求的目录约定。
- 2026-10-27：中英 help 只约定「内容与标题对齐」，排版各按各自文件习惯：中文版列表/表格/代码块里掺的空行不复制到英文版，英文保持紧凑列表与合法表格（否则表格会渲染成段落）。
